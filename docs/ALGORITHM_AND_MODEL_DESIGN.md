## 1. 边缘端模型选择

### 1）场景与模型候选

第一版文档采用MobileNetV3-Small和ResNet18构建通用图像分类Demo，适合验证EDGE/CLOUD分流
链路，但不能覆盖完整赛题要求。第二版按照两个正式场景和一个通用推理评测层分别选型：

| 层级 | 边缘侧候选 | 云端候选 | 主要任务 | 当前结论 |
|---|---|---|---|---|
| 工业视觉质检（当前主线） | YOLO系轻量检测器 / EfficientAD | 较强检测器 / PatchCore复核 | 缺陷定位、等级和处置动作 | 先冻结一类工件与缺陷集合，打通统一接口 |
| 工业声学（历史备选） | Log-Mel + 轻量AutoEncoder/轻量CNN | 预训练音频嵌入模型 + 异常原型库 | 正常、预警、故障判断 | 当前不接入，仅保留为扩展调研 |
| 交通单摄像头 | YOLOX-Tiny/轻量检测器 + ByteTrack | 较强检测器 + 轨迹修正 | 车辆检测与单摄像头跟踪 | 边侧输出轨迹，不上传全量视频 |
| 交通跨摄像头 | 轻量ReID特征 | ReID + 摄像头拓扑 + 时间窗关联 | 跨节点车辆身份统一 | CityFlowV2作为正式测试集 |
| 边侧通用推理 | 1B至1.5B指令模型4bit量化 | 7B以上强模型或云端API | 数学、代码、中文自然语言推理 | 通过GSM8K/HumanEval/C-Eval测能力保持率 |
| 安全规则 | 固定阈值和紧急动作规则 | 异步复核 | 断网及高风险任务兜底 | 规则不可被大模型覆盖 |

MobileNetV3-Small/ResNet18方案仍保留为早期图像分类对照，用于说明“全边缘、全云端、固定分流”
的基本差异，但不再作为最终双场景核心模型。

### 2）早期候选：工业声学模型（非当前提交主线）

早期候选曾选择MIMII DUE中的Fan和Pump，保留正常/异常以及source、target domain。边侧首先将
音频转换为Log-Mel频谱，再使用轻量AutoEncoder学习正常状态，异常分数可采用重构误差或
Mahalanobis距离：

```text
设备音频 → Log-Mel频谱 → 轻量异常检测模型
         → 异常分数 → normal / warning / critical
         → DREAM-CE路由与安全动作
```

该方案的优点是训练和推理流程成熟、异常分数可解释，并能在只有正常训练样本时建立基线。
不足是AutoEncoder在复杂噪声和域偏移下可能泛化不足，因此第二阶段再加入预训练音频嵌入、
source/target原型距离或知识蒸馏。

AI4I 2020可用于前期CSV接口和调度链路冒烟，但它属于合成表格数据，不应作为最终工业创新
证据。

### 3）交通场景模型

交通数据采用CityFlowV2中4至6个相邻摄像头、至少2个路口的子集。每个摄像头模拟一个边缘
节点，处理流程为：

```text
视频帧 → 车辆检测 → ByteTrack单摄像头跟踪 → ReID特征
      → 摄像头拓扑与合理通行时间过滤
      → 跨摄像头轨迹关联 → 多节点冲突仲裁
```

边缘侧优先上传检测框、轨迹、时间戳和压缩ReID特征，仅在低置信度、遮挡严重或身份冲突时
上传疑难帧。相比上传完整视频，该方案更符合低通信量和实时协同目标。

### 4）边侧轻量大模型

仓库已提供GGUF/llama.cpp模型适配接口，建议先使用约1B至1.5B的4bit量化指令模型作为候选，
并限制上下文长度和最大输出。具体模型不能只凭公开参数确定，必须在目标硬件上同时测量：

- GSM8K数学推理准确率；
- HumanEval代码通过率；
- C-Eval中文任务准确率；
- TTFT、输出速度和端到端时延；
- 进程峰值RSS、GPU专用显存增量；
- 模型加载时间和量化前后能力损失。

能力保持率定义为：

```text
能力保持率 = 边侧模型得分 / 云端模型得分 × 100%
```

只有在相同提示词、解码参数、评分脚本和测试集上对比，才能判断是否达到80%至90%的要求。

### 5）部署约束

1. 所有模型必须使用统一标签、动作和置信度接口，便于替换数据集或模型而不修改调度层；
2. 边侧模型以batch=1进行实时测试，预热后报告平均值、P50和P95；
3. 内存占用分别记录模型文件大小、进程峰值RSS和GPU专用显存，不混用不同口径；
4. 安全规则优先于模型输出，critical/incident事件不得等待云端返回；
5. 第一阶段不将模型切分、联邦学习和复杂在线训练作为MVP前置依赖，待基础链路和实测基线稳定
   后再开展消融实验。

## 2. 云边任务分流策略

### 已有方法

1. **固定比例分流：**实现简单，但不考虑样本难度、网络状态和节点负载，只适合作为弱基线；
2. **选择性分类：**边侧只接受高置信度结果，低置信度样本交给云端；
3. **Early Exit：**简单样本从中间出口返回，困难样本继续计算；
4. **模型切分：**边缘运行前半网络、云端运行后半网络并传输中间特征；
5. **资源感知卸载：**根据RTT、带宽、CPU、队列和任务SLA决定执行位置；
6. **LLM路由：**在小模型和强模型之间根据任务难度与代价动态选择；
7. **多节点投票：**多数投票或最高置信度选择，实现简单但容易被过度自信或过期节点误导。

现有方法可以分别解决部分问题，但没有一套方法直接同时覆盖本赛题的双场景、0.2秒时延、弱网
保持、多边缘冲突和边侧大模型能力指标。因此本项目采用DREAM-CE进行组合与改进。

### 可能采用：DREAM-CE

DREAM-CE全称为Deadline, Risk and Evidence-Aware Multi-edge Cloud-Edge，即面向截止时间、
风险和证据一致性的多边缘云边协同算法，由DREAM-Exit、DREAM-Route和DREAM-Fuse组成。

### 1）DREAM-Exit：动态本地退出

若任务风险为critical或边侧模型检测到critical/incident，立即执行本地安全动作，并在网络可用
时异步请求云端复核。普通任务的动态阈值为：

```text
T_dynamic = clip(
    T_base + A_risk - 0.18 × D_network - 0.08 × P_deadline,
    0.55,
    0.95
)
```

- `A_risk`：风险越高，阈值越高；
- `D_network`：由网络可用率、RTT、抖动和丢包率计算；
- `P_deadline`：已消耗deadline的比例。

高风险任务需要更强证据才能直接返回；网络恶化或deadline即将耗尽时降低本地退出阈值，使更多
任务留在本地，提升弱网业务保持率。

### 2）DREAM-Route：多路径约束路由

对PEER_EDGE、CLOUD和EDGE_FALLBACK构建候选执行配置，并计算：

```text
J(k) = L(k)/D
     + 2 × W_risk × (1-Q(k))
     + 2.5 × (1-A(k))
     + 0.25 × Load(k)
     + 0.05 × Comm(k)
     + Penalty(k)
```

- `L(k)`：预计完成时延；
- `D`：剩余deadline；
- `Q(k)`：模型预期准确率或节点历史可靠度；
- `A(k)`：路径可用率；
- `Load(k)`：节点负载；
- `Comm(k)`：通信量；
- `Penalty(k)`：超出deadline、远端不可用或被迫降级的惩罚。

算法优先尝试满足deadline且总代价最小的路径。当Peer或Cloud请求失败时，继续按照候选顺序尝试，
所有远端不可用时返回保守本地结果，保证有限时间内完成基本业务。

### 3）DREAM-Fuse：多边缘证据仲裁

边缘节点 `i` 的证据权重定义为：

```text
w_i = p_cal_i × reliability_i × freshness_i × topology_i × version_i
freshness_i = exp(-ln(2) × age_i / half_life)
topology_i = 0.5 + 0.5 × spatial_consistency_i
```

- `p_cal_i`：经过Temperature Scaling校准的置信度；
- `reliability_i`：节点历史正确率或可靠度；
- `freshness_i`：观测越旧，权重越低；
- `topology_i`：交通拓扑、合理通行时间或工业多传感器一致性；
- `version_i`：模型版本一致性系数。

支持相同`prediction + action`的节点证据相加：

```text
E(y) = Σ w_i
Consensus(y) = E(y) / Σ E(all outcomes)
```

共识达到阈值时自主仲裁；普通冲突共识不足时进入CLOUD复核；高风险且证据充分的紧急事件立即
执行本地安全动作。该机制比“取最高置信度”更能抑制过度自信、长期不可靠或观测过期的节点。

### 4）在线算法流程

```text
输入任务与deadline
  ↓
边侧模型/规则推理，得到prediction、confidence、risk
  ↓
critical/incident？── 是 → EDGE_SAFETY立即执行，云端异步复核
  │
  否
  ↓
DREAM-Exit计算动态阈值
  ├─ 置信度充分 → EDGE直接返回
  └─ 置信度不足
          ↓
DREAM-Route对PEER/CLOUD/FALLBACK排序
          ↓
关联任务存在多节点结果？
  ├─ 否 → 按最优可行路径执行
  └─ 是 → DREAM-Fuse证据仲裁
              ├─ 共识充分 → PEER_EDGE/EDGE_SAFETY
              └─ 共识不足 → CLOUD复核；超时则保守降级
```

### 5）阈值和参数确定

当前代码中的权重属于可解释初值，最终必须通过独立校准集和真实运行日志确定：

1. 使用校准集学习Temperature Scaling参数；
2. 扫描本地置信度阈值和共识阈值；
3. 在边缘接受错误率不超过目标上限的前提下提高边缘覆盖率；
4. 使用真实时延、节点正确率和网络可用率重新拟合路由代价；
5. 节点可靠度采用滑动窗口或指数移动平均在线更新；
6. 所有参数在验证/校准集选择，最终测试集只做一次报告评估。

### 2）必须比较的基线

1. **全边缘：**所有任务在原始边缘节点完成；
2. **全云端：**所有任务上传云端；
3. **固定比例分流：**例如固定50%请求上云；
4. **固定置信度分流：**只根据固定阈值选择EDGE/CLOUD；
5. **固定Peer优先：**低置信度任务总是先请求Peer；
6. **最高置信度仲裁：**发生冲突时直接选择confidence最高节点；
7. **DREAM-CE：**动态阈值、候选代价路由和证据仲裁完整方案。

### 3）赛题硬指标

```text
平均端到端时延 = Σ任务端到端时延 / 任务总数

弱网业务保持率 =
    网络异常期间完成基本功能的任务数 / 弱网任务总数

冲突率 =
    产生矛盾结果的关联任务数 / 多节点关联任务总数

冲突解决成功率 =
    最终决策与真值一致的冲突数 / 带真值冲突总数

能力保持率 =
    边侧模型得分 / 云端模型得分 × 100%

TTFT降幅 =
    (云端TTFT - 边侧TTFT) / 云端TTFT × 100%
```

比赛目标为：平均端到端时延不超过0.2秒；弱网期间基本业务保持率不低于90%；冲突率不高于
5%；冲突解决成功率不低于90%；边侧数学、代码、自然语言推理能力保持云端模型的80%至90%；
TTFT减少75%；单次推理内存不超过1.5GB。

### 4）指标口径注意事项

- `EDGE`正常接受与`EDGE_FALLBACK`被迫降级必须分开统计；
- 运行时`resolution_success`只表示是否形成稳定决策，不等于仲裁结果正确；
- 比赛仲裁成功率必须依赖真实标签或可验证事件结果；
- 内存同时报告峰值RSS和GPU显存增量，不能将模型文件大小当作运行内存；
- TTFT必须统一是否包含排队、网络、分词和模型冷启动；
- 端到端时延报告平均值、P50和P95，不能只报告模型内部推理时间；
- 对于不平衡异常数据，除Accuracy外还需报告Macro-F1、AUROC或pAUC。

### 5）网络压力矩阵

| 变量 | 建议取值 |
|---|---|
| RTT | 20、100、300、500ms |
| 丢包率 | 0%、1%、5%、10% |
| 断网时长 | 0、5、10、30秒 |
| 抖动 | 0、20、50、100ms |
| 边缘负载 | 低、中、高 |
| 冲突形式 | 标签相反、动作相反、过期观测、低可靠节点、模型版本不一致 |

### 6）消融实验

在工业和交通两个场景分别比较：

1. 固定阈值与DREAM-Exit；
2. 固定Peer优先与DREAM-Route；
3. 最高置信度仲裁与DREAM-Fuse；
4. 去掉节点可靠度；
5. 去掉观测新鲜度；
6. 去掉时空一致性；
7. 去掉低共识云端复核；
8. 正常网络、弱网和断网三组条件。

只有在上述对照中稳定降低时延/冲突或提高弱网完成率，DREAM-CE才能作为经过验证的创新点。

## 4. 对项目的建议

### 1）推荐的正式技术路线

> **工业视觉质量检测 + 交通CityFlowV2双场景感知，边侧轻量模型与4bit小型指令模型，结合
> DREAM-Exit动态退出、DREAM-Route多路径约束路由、DREAM-Fuse多边缘证据仲裁、紧急安全
> 动作和断网保守降级；通过GSM8K/HumanEval/C-Eval和网络冲突回放验证比赛全部硬指标。**

### 2）实现顺序

1. **先接数据：**建立统一数据清单、标签和训练/验证/校准/测试划分；
2. **再做场景基线：**工业先跑轻量缺陷检测/异常定位，交通先跑检测、跟踪和ReID；
3. **接入统一接口：**模型统一输出prediction、confidence、action、latency、model_version；
4. **校准和路由：**使用校准集确定温度、动态阈值和共识阈值；
5. **压力回放：**执行弱网、断网、多节点冲突和模型版本不一致实验；
6. **边侧模型实测：**固定硬件测试GSM8K、HumanEval、C-Eval、TTFT和内存；
7. **完成消融：**与全边缘、全云端、固定分流和最高置信度仲裁对比；
8. **最后整理演示：**展示正常任务、困难任务、网络波动和多节点冲突四类典型案例。

### 3）创新性表述建议

可以表述的创新点：

1. 将不确定性、任务风险、网络、负载和剩余deadline统一到可解释的多路径路由代价中；
2. 使用校准置信度、节点可靠度、观测新鲜度和时空一致性进行多边缘证据仲裁；
3. 将紧急本地安全动作与普通低共识云端复核分离；
4. 通过统一感知接口支持工业、交通及后续能源场景扩展；
5. 区分“成功返回结果”和“带真值仲裁正确”，建立可审计的比赛指标口径。

不能直接表述的内容：

- 不能将AutoEncoder、ByteTrack、ReID、AWQ或Temperature Scaling本身声明为原创；
- 在没有消融实验前，不能宣称DREAM-CE一定优于现有算法；
- 在没有真实数据前，不能宣称达到0.2秒、90%、5%、75%或1.5GB指标；
- 不能把单元测试通过率当作模型准确率或系统稳定性指标。

### 4）当前需要项目组确认的信息

1. 最终边缘硬件是电脑模拟、树莓派、Jetson还是其他设备；
2. 云端和边侧候选大模型及是否允许调用外部API；
3. 是否允许使用预训练模型、开源权重和迁移学习；
4. 工业视觉、CityFlow及通用推理数据集的本地路径和许可情况；
5. 可接受的训练时间、存储容量和GPU资源；
6. 现场演示使用的设备、网络和是否能够人为控制弱网条件；
7. 最终评分更偏重算法创新、系统完整性还是现场可视化效果。
