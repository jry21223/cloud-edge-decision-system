# 云边协同任务调度模块：论文调研、算法设计与验收方案

> 版本：v0.1
> 日期：2026-08-10
> 状态：匿名技术交付稿，可用于组内评审、作品报告和实验任务拆分
> 应用主线：工业视觉检测；第二场景：交通监控最小 Adapter

实现级数据契约、deadline 预算、在线估计器、动态权重、状态机、接口和实验字段见 `SCHEDULER_TECHNICAL_SPEC.md`。本文负责论文依据、创新边界与验收设计；实现规格负责把这些内容落实到代码可执行语义。

## 1. 本模块的职责与交付边界

本模块负责回答四个问题：

1. 现有云边协同调度方法解决了什么问题；
2. 这些方法为什么不能直接满足本赛题的工业视觉场景；
3. 本项目的动态评分调度策略究竟新增了什么机制；
4. 如何用代码、日志和对照实验证明创新有效。

本模块不负责从零训练视觉基础模型，也不负责把全部业务逻辑集中到 Controller。调度器只消费模型输出、任务约束、网络状态和节点状态，通过统一接口在本地闭环、Peer Edge、Cloud 与安全回退之间选路。

需要形成以下可验收交付物：

- 一份代表性论文对比矩阵；
- 一套任务-系统双感知的安全约束调度算法；
- 一份与当前代码的字段、接口和状态机映射；
- 一套基线、消融、弱网和多节点实验；
- 可直接写入申报书/PPT的创新表述；
- 每项结论对应的 CSV、trace 和图表证据。

## 2. 官方要求对调度模块的约束

口径优先级：11 页正式比赛方案高于 2 页早期项目简介。早期简介中的“边缘先判、低置信度上云”只能作为基线，不能覆盖正式方案新增的弱网、双场景、端到端时延和一致性硬指标。

| 官方要求 | 调度模块必须承担的责任 | 不能采用的模糊口径 |
|---|---|---|
| 云边协同技术效果 40 分 | 与 Cloud-only、Edge-only 等基线比较时延、效果和通信 | 只展示一次 Demo 或只报平均值 |
| 弱网基本业务保持率不低于 90% | 远端不可用时本地安全闭环、有限等待和保守回退 | 把“HTTP 返回成功”当作业务功能保持 |
| 至少 2 类差异明显场景 | 同一调度内核复用，场景只通过 Adapter 提供任务特征和动作约束 | 复制两套互不相干代码冒充可扩展性 |
| 平均端到端时延不超过 0.2 s | 约束候选路径，分别记录路径时延并汇总总体平均值 | 只统计 Edge 路径或排除超时任务 |
| 多节点冲突比例不高于 5% | 明确定义关联任务、冲突和去重窗口 | 以请求失败数代替决策冲突数 |
| 冲突解决成功率不低于 90% | 使用带真值冲突样本验证最终决策是否正确 | 把“成功返回某个结果”当作正确解决 |
| 代码、数据、视频和报告 | 调度输入、候选得分、剔除原因、最终路径全量留痕 | 只给公式而没有可复现运行证据 |

边侧轻量大模型的能力保持率、TTFT 和 1.5 GB 指标与工业视觉指标并不完全同构。项目应保留一条独立的国产开源轻量模型基准支线，但不能用该支线替代工业视觉调度实验。

## 3. 现有方法分类与代表论文

### 3.1 模型切分与早退

| 工作 | 核心机制 | 解决的问题 | 对本项目的不足 | 可借鉴点 |
|---|---|---|---|---|
| [Neurosurgeon, ASPLOS 2017](https://doi.org/10.1145/3037697.3037698) | 按 DNN 层在移动端与云端间自动选择切分点 | 降低时延、移动端能耗和云端压力 | 依赖同一模型的层级切分，默认相对稳定的剖析结果；不处理业务风险、多节点冲突和安全动作 | 将通信与计算共同纳入预计完成时间 |
| [DADS, IEEE INFOCOM 2019](https://doi.org/10.1109/INFOCOM.2019.8737614) | 根据网络条件对 DAG 型 DNN 动态切分；轻载优化时延，重载优化吞吐 | 适应网络与负载变化，减少中间数据传输 | 求解与模型拓扑强耦合，不适合“Edge 检测器 + Cloud 多模态模型”的松耦合组合 | 将轻载/重载状态区别处理，显式考虑吞吐与时延目标 |
| [Edgent, IEEE TWC 2020](https://doi.org/10.1109/TWC.2019.2946140) | 联合选择模型切分点和早退点；用回归预测延迟并适应带宽变化 | 在 deadline 内尽量提高推理精度 | 主要优化单设备-单边缘的切分与早退；没有多工位、故障回退和质量风险 | 离线 profiling + 在线轻量决策；deadline 作为硬约束 |
| [SPINN, ACM MobiCom 2020](https://doi.org/10.1145/3372224.3419194) | 运行时联合优化 early exit 与 device-cloud split | 动态连接下兼顾准确率、吞吐和服务等级 | 同样依赖可切分的 CNN；不适合异构模型与 ROI/原图分级上传 | 把服务等级目标和渐进式推理结合，而非固定阈值 |

结论：模型切分类方法证明了“计算时延 + 通信时延 + deadline”必须联合建模，但本项目不应照搬模型切分。工业视觉采用边缘轻量检测器与云端视觉/多模态模型，两个模型应松耦合，通过任务级路由协同。

最直接的研究空白不是“以前没人做动态评分”，而是：现有工业视觉工作通常只感知任务难度，或只感知系统资源；对生产 deadline、缺陷风险、数据上传粒度、远端故障和多工位冲突的统一处理不足。

## 4. 本项目要解决的调度问题

每个任务 `t` 具有：

```text
x_t = {
  uncertainty, scene_complexity, image_quality,
  risk_level, critical_region, deadline_ms,
  roi_bytes, raw_bytes, allowed_actions
}
```

每个候选节点或路径 `n` 具有：

```text
z_n = {
  availability, rtt_ms, jitter_ms, packet_loss, bandwidth,
  queue_depth, service_time_ms, cpu_gpu_load,
  model_version, task_compatibility, historical_reliability
}
```

调度器输出联合决策：

```text
d_t = (route, target_node, upload_mode, timeout_ms, fallback_action)
```

其中 `route` 属于 `EDGE`、`PEER_EDGE`、`CLOUD`、`EDGE_FALLBACK`、`EDGE_SAFETY`，`upload_mode` 属于 `METADATA`、`ROI`、`RAW`。

## 5. 建议方案：任务-系统双感知的安全约束动态评分

内部代码可继续使用 `DREAM-Route` 名称，竞赛表述使用“任务-系统双感知的安全约束动态评分调度”，避免只靠缩写制造创新感。

### 5.1 第一阶段：本地安全门控

```text
if image_quality_failed:
    QUARANTINE
elif critical_region_hit or severe_defect:
    EDGE_SAFETY + optional ASYNC_CLOUD
elif high_confidence_normal and pass_guard_satisfied:
    EDGE -> PASS
elif high_confidence_known_defect:
    EDGE -> REJECT
else:
    request Controller routing
```

重要约束：弱网不能降低 `PASS` 安全门槛。对于高风险或关键部位，远端不可用时应隔离复检，不能因为网络差就更容易判为正常。低风险、非关键任务可以调整“是否同步上云、进入抽检或隔离队列”的升级流量策略，但不能绕过已经冻结的本地放行 guard；任何降级路径都必须标记 `degraded=true`。

### 5.2 第二阶段：候选可行性过滤

先计算剩余预算，再预测候选从“当前时刻开始”的未来耗时：

```text
R(t) = deadline_ms - elapsed_ms

T_future(t,n,m) = controller_time
                + queue_wait_n
                + inference_time_n
                + RTT_n
                + 8 * bytes(t,m) / goodput_bps_n * 1000
                + return_and_action_time
```

`elapsed_ms` 已经从 deadline 中扣除，不能再加入 `T_future`，否则会重复扣减。正式实现使用 P95 预测，并额外保留 deadline guard 与本地回退预算。

若出现以下任一情况，远端候选直接判为不可行，不仅是增加一个小惩罚：

- `T_future_p95 + deadline_guard + fallback_reserve > R(t)`；
- 节点不可用或连续失败触发熔断；
- `hop_count > 1`；
- 模型/场景/输入格式不兼容；
- 上传模式违反任务隐私或数据策略；
- 目标节点没有足够内存或队列已封顶。

### 5.3 第三阶段：对可行候选动态评分

对可行路径计算归一化代价：

```text
J(t,n,m) = w_L(t) * latency_ratio
         + w_E(t) * expected_error
         + w_B(t) * upload_ratio
         + w_Q(t) * load_ratio
         + w_F(t) * failure_risk
         + w_P(t) * privacy_cost
```

动态权重不是每次随意变化，而是由任务状态确定：

```text
w_E(t) = w_E0 * (1 + lambda_r * risk + lambda_u * uncertainty)
w_L(t) = w_L0 * (1 + lambda_d * deadline_pressure)
w_B(t) = w_B0 * (1 + lambda_n * network_degradation)
w_F(t) = w_F0 * (1 + lambda_n * network_degradation)
```

- 高风险、高不确定任务提高错误代价；
- deadline 越紧，提高时延代价；
- 网络越差，提高通信和失败代价；
- 权重必须用验证集和网络 trace 标定，并在测试集实验前冻结。

选择 `J` 最小的可行候选，并记录每个分量、剔除原因与策略版本。不能只记录一句“网络不好所以本地处理”。

### 5.4 预期准确率与可靠度不能写死

当前原型使用固定的 Cloud 预期准确率和节点可靠度，只能用于联调。正式实验应按“模型版本 + 场景 + 难度分桶”统计：

```text
Reliability[n, model, difficulty](t)
  = rho * Reliability(t-1) + (1-rho) * correct_label
```

只有获得 Cloud/人工确认真值后才更新。样本不足时使用保守先验，防止少量成功记录让新节点获得过高权重。

### 5.5 抑制路由抖动

- RTT、队列和负载使用 EWMA 平滑；
- 两条候选代价差小于 `hysteresis_margin` 时保持当前目标；
- 连续失败达到阈值后触发短时熔断；
- 恢复时先灰度放量，不立即接收全部任务；
- 调度决策本身必须有最大耗时预算。

## 6. 相比现有工作的可辩护创新点

### 核心机制

任务难度与系统状态双感知的安全约束动态评分：同时使用模型不确定性、图像复杂度、缺陷风险、deadline、网络、队列、负载和历史可靠度，先过滤不可行路径，再在可行集合中评分。

### 配套能力 1：路由与上传粒度联合决策

Controller 不接收完整图像，只返回目标与 `METADATA/ROI/RAW` 上传模式；Edge 将数据直传目标节点。上传字节数直接进入评分，降低 Controller 带宽压力。

### 配套能力 2：安全优先的可恢复回退

严重缺陷先在 Edge 隔离或报警；远端超时后不让迟到结果覆盖已执行动作；任务和 ROI 写入 outbox，恢复后补传用于追溯和模型更新。

### 配套能力 3：多节点证据与历史可靠度

同一工件的多工位结果用 `workpiece_id + station_id + time_window` 关联；按校准置信度、可靠度、新鲜度和空间一致性融合。低共识上云，高风险证据先触发保守动作。

### 不能宣称的内容

- 不能声称首次提出云边协同或动态评分；
- 未完成全局最优证明时，不能称“最优调度”；
- 未完成消融前，不能把组合机制写成已验证创新；
- AIVD、SAEC 等仍是预印本，引用时必须标明状态；
- 规则样例不能证明感知精度、冲突解决率或能力保持率。

## 7. 基线与消融实验

### 7.1 主基线

| 编号 | 策略 | 验证目的 |
|---|---|---|
| B1 | Cloud-only | 精度上限、远端依赖、通信和时延基线 |
| B2 | Edge-only | 本地时延、资源和复杂样本能力基线 |
| B3 | Fixed Confidence Cascade | 证明多约束调度优于“低置信度就上云” |
| B4 | Resource-only Score | 模拟 AIVD 类只看节点资源的策略 |
| B5 | Task-only Complexity | 模拟 SAEC/难例路由，只看样本难度 |
| B6 | Small-scale Offline Oracle | 小规模整数规划/穷举最优解，测量在线评分与上界的差距 |
| P | Full Scheduler | 任务 + 系统 + 硬约束 + 上传模式 + 回退 |

### 7.2 必须消融

1. 去掉业务风险；
2. 去掉 deadline 硬过滤，改为软惩罚；
3. 去掉网络状态；
4. 去掉队列和负载；
5. 去掉历史可靠度；
6. 固定权重替代动态权重；
7. 去掉 EWMA/迟滞/熔断；
8. 固定 RAW 上传替代分级上传；
9. 去掉 Peer Edge；
10. 去掉安全回退。
11. 去掉置信度校准；
12. 去掉 SLO 慢速反馈环。

### 7.3 扰动条件

- 网络：基线、额外 100/300 ms、1%/5%/10% 丢包、5/10/30 s 断网；
- 资源：Edge/Cloud 队列过载、CPU/GPU 限额、Peer 空闲或繁忙；
- 任务：正常、已知缺陷、低置信难例、关键区域严重缺陷、图像质量失败；
- 多节点：一致、冲突、重复请求、乱序返回和模型版本不一致。

### 7.4 指标与统计规则

| 目标 | 指标 | 统计要求 |
|---|---|---|
| 实时性 | mean、P50、P95、P99、deadline 达成率 | 超时和失败不得从分母删除 |
| 感知/决策 | Precision、Recall、F1、严重缺陷漏检率 | 使用同一测试集与同一真值 |
| 通信 | 上云率、ROI/RAW 比例、每任务与总上传字节 | 从实际请求体或网络记录获得 |
| 稳定性 | 业务保持率、回退成功率、超时率、恢复时间 | “完成”必须定义为产生可执行业务动作 |
| 一致性 | 冲突率、正确解决率、重复决策率 | 只在有关联关系和真值的样本上计算 |
| 资源 | CPU/GPU、内存、显存、队列、功耗（可选） | 记录采样周期、设备和模型版本 |

至少报告 3 次独立重复或 bootstrap 置信区间，避免只展示最好的一次运行。

### 7.5 提交前冻结的指标定义

```text
latency_e2e = t_action_ready - t_input_accepted

business_retention =
  弱网期间在业务 deadline 内产生允许终态的任务数
  / 弱网期间注入任务总数

conflict_rate =
  出现矛盾原始提案的唯一关联任务组数
  / 所有满足多节点关联条件的任务组数

resolution_success_rate =
  最终结果与真值一致的冲突任务组数
  / 所有带真值的冲突任务组数
```

- `t_input_accepted` 从系统接受图像/任务开始，`t_action_ready` 到 `PASS/REJECT/QUARANTINE/ALERT` 等现场动作可执行为止；排队、预处理、网络、Controller 和失败尝试都计入；
- 工业与交通场景、各种弱网条件分别统计，不允许通过混合不同条件稀释不达标结果；
- 业务保持不能只看 HTTP 200；超时结果和高风险错误放行均不算有效完成，同时报告误隔离率和严重缺陷漏检率；
- 冲突率应在正常业务分布上统计；解决率应在独立的带真值冲突集上统计；“返回一个最终结果”不等于解决正确；
- 正式竞赛配置应新增 `200 ms` profile。仓库当前 `800 ms` 默认 deadline 和 `350 ms` Cloud 延时仅适合联调，不能作为达标证据。

## 8. `0.2 s` 指标的现实约束

当前原型默认 Cloud 推理延迟为 350 ms。若 Edge 路径为 40 ms、Cloud 路径为 350 ms，忽略其他开销时，总体平均值要低于 200 ms，Cloud 路由比例必须满足：

```text
(1-p_cloud) * 40 + p_cloud * 350 < 200
p_cloud < 0.516
```

因此当前系统只有在超过约一半任务留在 Edge 时，平均值才可能达标；加上队列、上传和 Controller 开销后，允许的上云比例还要更低。这不是通过修改日志统计方式解决的问题，而是必须依靠本地高覆盖率、ROI 上传、Cloud 加速和 deadline 过滤共同实现。

报告应同时给出：

- 全部任务总体平均时延；
- 每条路径的平均/P95；
- Cloud 路由比例；
- 超时任务数量；
- 0.2 s 内完成的任务比例。

### 代码审计后的准确成熟度口径

截至 2026-08-10，仓库已有可演示的路由骨架，但只能称为“基于可注入状态的启发式评分原型”，不能称为已经验证的在线自适应调度系统，原因如下：

- RTT、丢包、Cloud 预计时延等主要来自任务 metadata 或固定默认值，Edge 心跳负载也主要来自环境变量，不是真实遥测；
- remaining deadline 只在 Controller 入口计算，Peer 失败后尝试 Cloud 前没有扣除已耗时间，尚未形成严格端到端硬约束；
- 计划阶段评分的 Peer 与执行阶段重新选择的 Peer 可能不同，计划和执行证据不能一一对应；
- 工业输入仍是温度、振动、电流等规则样例，尚无真实图像、ROI、bbox 或异常图；
- 多节点仲裁是独立 API，低共识只标记 Cloud 复核，没有在主任务链路真正完成复核闭环；
- Recorder 尚不能直接给出 P95/P99、deadline 达成率、弱网业务保持率、实际上传字节、视觉准确率等竞赛证据；
- 旧算法稿仍以 MIMII 工业音频为例，与工业视觉主线不一致，应由本稿的场景口径取代。

P0 实施顺序应固定为：先补齐 trace 与评分分项日志；再修正绝对 deadline 和计划-执行一致性；随后接入真实遥测与最小视觉 Adapter；最后接通 Cloud 复核、Recorder 指标和实验 runner。未完成前，报告只能写“已设计/原型已实现”，不能写“指标已达到”。

每条正式调度记录至少应输出：`trace_id`、场景、真值、任务风险、剩余 deadline、网络快照、节点状态、全部候选及剔除原因、各评分分量、最终 route/target/upload_mode/timeout、预计与实际分阶段时延、上传字节、最终动作、是否 deadline 内完成、模型与策略版本。

## 10. 可直接用于报告的创新表述

> 面向工业视觉检测中任务难度、生产风险与系统资源同时动态变化的问题，本项目设计任务-系统双感知的安全约束动态评分调度机制。该机制首先依据严重缺陷、deadline、节点可用性和模型兼容性过滤不可行路径，再融合模型不确定性、场景复杂度、网络质量、队列负载、历史可靠度和上传量，在 Edge、Peer Edge、Cloud 与 Fallback 间进行可解释选路；同时将上传粒度和故障回退纳入统一决策，实现常规样本边缘闭环、疑难样本按需增强、高风险任务现场先处置以及弱网条件下业务可恢复。

建议只把上段作为一项核心机制，再用“分级上传”和“安全回退/多工位一致性”作为系统能力，不要把每个公式项分别包装成创新点。

## 12. Grilling：提交前必须回答的十个问题

1. `expected_accuracy=0.96` 的数据来源是什么？若无验证集，它只能叫占位参数。
2. 动态权重如何确定？若只是拍脑袋，为什么不是另一组权重？
3. Cloud 结果超过现场 deadline 后，是否仍会覆盖已经执行的剔除/隔离动作？
4. 弱网降低阈值时，如何证明不会提高严重缺陷漏检率？
5. Controller 当前代理 Cloud 图像请求，凭什么声称控制/数据平面分离？
6. 冲突率的分母是什么，如何判定两个结果属于同一工件或关联任务？
7. “冲突解决成功”是否有真值，还是只表示接口返回成功？
8. 第二场景除字段名称外，任务分布、deadline 和动作约束哪里真正不同？
9. 0.2 s 平均值是否包含超时、失败、Cloud 路径和图像上传？
10. 去掉风险、deadline、网络或负载后，完整策略是否仍显著更好？若没有，创新点应如何收缩？

只有这些问题都有日志、数据或明确的系统规则回答，调度模块才算完成。
